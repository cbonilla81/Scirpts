01 / Design

Deployment architecture

The management workstation authenticates to the Proxmox HTTPS API. Proxmox full-clones the Windows 11 template. A Windows management machine later connects over trusted WinRM HTTPS to perform AD joins.

02 / Readiness

Prerequisites and capacity planning

Proxmox infrastructure

  • Proxmox VE 9 target node and accessible HTTPS API (TCP 8006)
  • Template VM ID 9000 on configured template node
  • Available VM IDs 2200–2209
  • Suitable datastore for full clones and EFI/TPM disks
  • Windows-capable network bridge, VLAN and DHCP

Windows and AD infrastructure

  • Valid Windows 11 licensing and compatible VM hardware
  • Domain DNS, reachable DCs, synchronized time
  • Management workstation with Terraform + PowerShell
  • Local guest admin and delegated domain join account
  • Trusted WinRM HTTPS listener and firewall access

03 / Golden image

Build a reliable Windows 11 template

STEP 1

VM hardware

Use OVMF (UEFI), q35, TPM 2.0, EFI disk, VirtIO SCSI storage and VirtIO networking. Confirm Secure Boot compatibility and adequate disk capacity.

STEP 2

Install & update

Install Windows 11, VirtIO drivers, QEMU Guest Agent, required baseline software, security updates and guest firewall policy.

STEP 3

Generalize & convert

Remove secrets and machine-specific identity, run Sysprep, shut down, validate clone behavior, then convert to template in Proxmox.

PowerShell
C:\Windows\System32\Sysprep\Sysprep.exe /generalize /oobe /shutdown
Windows 11 TPM caution: verify your template cloning procedure does not unintentionally duplicate machine-specific TPM state or credentials. Test cloning with the exact Proxmox version, template layout and security baseline before mass deployment. Do not domain-join the golden image.

04 / Authentication

Proxmox API account and token

Create a dedicated automation identity and token using the Proxmox UI under Datacenter → Permissions → Users / API Tokens, or use the CLI with an appropriate access model. Assign only the permissions needed for clone, VM configuration and storage access.

PowerShell
pveum user add terraform@pve --comment "Terraform deployment identity"
pveum user token add terraform@pve deployment --privsep 0
The token command above does not grant VM privileges by itself. Grant the service account appropriate scoped permissions before deploying. --privsep 0 inherits the account's permissions; consider privilege-separated tokens and scoped ACLs in production. Avoid cluster-wide PVEAdmin unless this is an isolated lab.

Set the endpoint and token for your current PowerShell process using the included helper:

PowerShell
.\scripts\Set-ProxmoxEnvironment.ps1 -Endpoint "https://pve1.example.com:8006/"

Prefer a CA-trusted Proxmox API certificate. The script prompts for the token instead of writing it into .tf files.

07 / Execute

First deployment: one VM, then ten

  1. Extract the project ZIP and open PowerShell in its root directory.
  2. Configure your API endpoint/token in the same shell.
  3. Copy and edit terraform.tfvars; confirm node names, template VM ID and available VM IDs.
  4. Start with vm_count = 1, review the plan, then deploy.
  5. After Windows guest validation, set vm_count = 10 and apply again.
PowerShell
cd .\terraform
Copy-Item .\terraform.tfvars.example .\terraform.tfvars
notepad .\terraform.tfvars
terraform init
terraform fmt -check
terraform validate
terraform plan -out=deployment.tfplan
terraform apply deployment.tfplan
terraform output vm_inventory
Review every plan: VM IDs 2200–2209 must be unused. Terraform state is authoritative for managed resources. Never casually reinitialize a fresh state against already-deployed infrastructure, and do not commit state or plan files that may contain sensitive values.

08 / Guest customization

Windows first boot and Active Directory join

Domain join is a separate operational stage. First complete OOBE, ensure the guest has a reachable IP address, working domain DNS and time synchronization, and provision a trusted WinRM HTTPS listener on TCP 5986. The included scripts do not set up those prerequisites.

Network prerequisites

  • Guest can resolve the AD domain and domain controllers
  • Guest can reach required AD DS services
  • Windows controller can connect to guest TCP 5986
  • WinRM certificate SAN matches the endpoint used in CSV
  • Guest local admin account is usable after Sysprep

Credential safeguards

  • Interactive local administrator credentials
  • Interactive delegated domain-join credentials
  • No password in terraform.tfvars
  • Use Windows LAPS after domain join
  • Do not bypass TLS certificate validation

A. Export inventory

PowerShell
cd ..
.\scripts\Export-VMInventory.ps1

Populate the IPAddress field in scripts/vm-inventory.csv from DHCP leases or QEMU Guest Agent data. For WinRM HTTPS, prefer a DNS name in that field if the certificate is issued to a DNS name; despite the column label, the script passes the field directly as the connection target.

B. Preview domain join

PowerShell
.\scripts\Join-WindowsDomain.ps1 -CsvPath .\scripts\vm-inventory.csv -DomainName "corp.example.com" -OUPath "OU=Workstations,DC=corp,DC=example,DC=com" -WhatIf

C. Execute domain join

PowerShell
.\scripts\Join-WindowsDomain.ps1 -CsvPath .\scripts\vm-inventory.csv -DomainName "corp.example.com" -OUPath "OU=Workstations,DC=corp,DC=example,DC=com"

The script prompts for credentials, connects to each guest, runs Add-Computer with the requested new name and OU, then requests a reboot. It processes guests sequentially. Review results individually; a connection interruption during reboot is not necessarily evidence of join failure.

Exact supplied domain-join implementation

scripts/Join-WindowsDomain.ps1
# Requires Windows PowerShell 5.1 or PowerShell 7 on Windows and WinRM over HTTPS
# with trusted guest certificates. Run only on your authorized Windows machines.
[CmdletBinding(SupportsShouldProcess = $true, ConfirmImpact = 'High')]
param(
  [Parameter(Mandatory)][string]$CsvPath,
  [Parameter(Mandatory)][string]$DomainName,
  [string]$OUPath,
  [switch]$SkipCertificateValidation
)
$ErrorActionPreference = 'Stop'
if ($SkipCertificateValidation) { throw 'Certificate validation bypass is intentionally unsupported. Install trusted WinRM HTTPS certificates instead.' }
$rows = Import-Csv $CsvPath
if (-not $rows) { throw 'Inventory CSV is empty.' }
$localCred = Get-Credential -Message 'Enter the local administrator credentials on the sysprepped Windows 11 clones'
$domainCred = Get-Credential -Message "Enter AD credentials authorized to join machines to $DomainName"
foreach ($row in $rows) {
  $name = $row.Name
  $ip = $row.IPAddress
  if ([string]::IsNullOrWhiteSpace($ip)) { Write-Warning "Skipping $name: IPAddress is blank"; continue }
  if ($name -notmatch '^[A-Za-z0-9-]{1,15}$') { Write-Warning "Skipping invalid NetBIOS hostname: $name"; continue }
  if (-not $PSCmdlet.ShouldProcess("$name ($ip)", "Rename and join $DomainName (reboots guest)")) { continue }
  try {
    # Certificate must be valid for the DNS name or IP used to connect.
    $s = New-PSSession -ComputerName $ip -UseSSL -Credential $localCred -Authentication Negotiate -ErrorAction Stop
    try {
      Invoke-Command -Session $s -ArgumentList $name,$DomainName,$OUPath,$domainCred -ScriptBlock {
        param($ComputerName,$Domain,$OU,$JoinCredential)
        $params = @{ DomainName=$Domain; NewName=$ComputerName; Credential=$JoinCredential; Force=$true; ErrorAction='Stop' }
        if ($OU) { $params.OUPath = $OU }
        Add-Computer @params
        Restart-Computer -Force
      } -ErrorAction Stop
      Write-Host "Join submitted for $name; wait for reboot and verify AD membership."
    } finally { Remove-PSSession $s -ErrorAction SilentlyContinue }
  } catch {
    Write-Warning "Failed $name : $($_.Exception.Message)"
  }
}
09 / Verification

Confirm success at every layer

Terraform / Proxmox

  • terraform state list shows ten VM resources
  • All ten VM IDs exist on the intended node
  • Each guest boots, has a NIC and a healthy guest agent
  • Cloned disks, EFI and TPM are present

Windows / AD

  • Expected computer name after reboot
  • Windows reports PartOfDomain = True
  • Domain name and OU are correct
  • AD computer object exists and secure channel validates
  • DNS resolution and domain sign-in work
PowerShell
terraform state list
terraform output vm_inventory
# Run on each Windows guest after reboot:
Get-CimInstance Win32_ComputerSystem | Select-Object Name,Domain,PartOfDomain
Test-ComputerSecureChannel
# Run on an admin workstation with RSAT:
Get-ADComputer -Identity "WIN11-01" -Properties DistinguishedName
The included Test-DomainMembership.ps1 checks DNS resolution only. DNS success does not prove that a computer is domain-joined. Use the Windows guest and AD checks above for authoritative verification.
10 / Lifecycle

Scale safely and recover

Scale up

Change vm_count from 1 to 10 and run a new plan. Nine additional named resources should be proposed.

Scale down

Reducing vm_count removes higher-numbered resources from the desired configuration. Review potential VM/disk destruction carefully.

Recover

Back up VMs and Terraform state. Use Proxmox backup/restore and Terraform state reconciliation as separate controlled procedures.

PowerShell
terraform plan
terraform apply
# Destructive: only after reviewing the plan and backups
terraform plan -destroy
Do not use terraform destroy as a routine rollback. It removes managed VMs and associated disks. A failed AD join should normally be remediated in the guest, not by destroying all infrastructure.

12 / Operational controls

Security checklist and source references

  • Use least-privilege Proxmox service account and scoped token
  • Protect terraform.tfstate, saved plans and local inventories
  • Use trusted HTTPS certificates for Proxmox and WinRM
  • Delegate domain-join rights to a restricted OU, not Domain Admins
  • Use secure guest bootstrap, Windows LAPS and patch management
  • Audit Terraform changes, API actions and AD computer creation
  • Validate the first clone before scaling to ten
