1. Prepare Windows Server

1.1 Verify domain and SMB connectivity

On DATAMOVER01, launch PowerShell as Administrator.

PowerShell 
Get-ComputerInfo | Select-Object CsName, WindowsProductName, CsDomain
Test-ComputerSecureChannel
Get-Service LanmanWorkstation
Test-NetConnection FS01 -Port 445
Test-NetConnection FS02 -Port 445

Expected: Correct domain, True secure-channel result, running SMB client, and TCP 445 connectivity to both file servers.

1.2 Verify Robocopy

PowerShell 
Get-Command robocopy.exe
robocopy /?

Robocopy normally ships with supported Windows Server releases. No Rclone installation is needed.

1.3 Create application directories

PowerShell 
New-Item -ItemType Directory -Force -Path `
  'C:\DataMover', 'C:\DataMover\Logs', `
  'C:\DataMover\Config', 'C:\DataMover\Data'

Restrict configuration and executable directories to Administrators, SYSTEM, and required service identities. Ordinary console users should not have filesystem write access to worker binaries.

2. Provision the gMSA

Run AD provisioning from a domain administration workstation with the ActiveDirectory PowerShell module.

2.1 Inspect KDS root keys

PowerShell 
Import-Module ActiveDirectory
Get-KdsRootKey

If none exists, coordinate this domain-level change with your AD team:

AD administrator only 
Add-KdsRootKey -EffectiveImmediately
In production, allow time for key availability and domain controller replication. Do not use lab-only backdating shortcuts.

2.2 Create authorized host group

PowerShell 
New-ADGroup -Name 'GG_DataMover_Hosts' `
  -SamAccountName 'GG_DataMover_Hosts' `
  -GroupScope Global -GroupCategory Security

Add-ADGroupMember -Identity 'GG_DataMover_Hosts' `
  -Members 'DATAMOVER01$'

2.3 Create the gMSA

PowerShell 
New-ADServiceAccount `
  -Name 'svc_DataMover' `
  -DNSHostName 'svc_DataMover.contoso.com' `
  -PrincipalsAllowedToRetrieveManagedPassword 'GG_DataMover_Hosts'

Get-ADServiceAccount svc_DataMover `
  -Properties PrincipalsAllowedToRetrieveManagedPassword

2.4 Install and verify on DATAMOVER01

PowerShell 
Import-Module ActiveDirectory
Install-ADServiceAccount -Identity svc_DataMover
Test-ADServiceAccount -Identity svc_DataMover
Gate: Test-ADServiceAccount should return True before proceeding. If it returns False, check replication, KDS readiness, computer group membership, DNS, and Kerberos; restart the host if necessary to refresh computer membership.

3. Delegate SMB and NTFS access

Use least-privilege permissions on approved shares. The gMSA does not need Domain Admin membership.

3.1 Create the migration access group

PowerShell 
New-ADGroup -Name 'GG_DataMover_Migration' `
  -SamAccountName 'GG_DataMover_Migration' `
  -GroupScope Global -GroupCategory Security

Add-ADGroupMember -Identity 'GG_DataMover_Migration' `
  -Members 'svc_DataMover$'

3.2 Inspect source and destination permissions

On the appropriate file server, verify the share and underlying NTFS security settings:

PowerShell 
Get-SmbShareAccess -Name 'SharedData'
Get-Acl 'D:\Shares\SharedData' | Format-List

Grant the gMSA group only the required source read and destination write capabilities, including security metadata access as needed. Share and NTFS permissions are evaluated together.

PrivilegeUse
SeBackupPrivilegeRead using backup semantics
SeRestorePrivilegeRestore file content and ownership
SeSecurityPrivilegeRead/write SACLs when required
Critical: Privileges needed for remote SMB access must be effective on the relevant file servers. Privileges granted only on DATAMOVER01 do not automatically apply on FS01 or FS02. /COPYALL requests data, attributes, timestamps, DACL, owner, and SACL; support and authorization must be validated.

cd C:\DataMover

Copy-Item .env.example .env

Protect .env and application data with restrictive NTFS ACLs.

4.2 Implement the separate worker before production

Required software development: The current v1.2 package does not yet include a dedicated worker entry point. Implement an authenticated local job channel, strict path allowlists, approved Robocopy options, subprocess execution without a shell, process monitoring, job locking, persistent audit records, and restart reconciliation.

Only after the worker is implemented should it be installed as a Windows service under CONTOSO\svc_DataMover$ with Log on as a service rights and recovery settings. Do not run the web API itself under the privileged migration gMSA.

6. Run a representative pilot

6.1 Create test data

On FS01, create a dedicated pilot directory and publish it through an approved test SMB share. Create a corresponding destination share on FS02.

PowerShell on FS01 
New-Item -ItemType Directory -Force `
  -Path 'D:\Shares\DataMoverPilot'
'DataMover test' | Set-Content `
  'D:\Shares\DataMoverPilot\test.txt'

6.2 Perform a Dry-Run

Execute as the intended worker identity, not merely as an interactive administrator.

PowerShell 
robocopy '\\FS01\DataMoverPilot' '\\FS02\DataMoverPilot' `
  /E /L /COPYALL /DCOPY:DAT /R:0 /W:0 /XJ /TEE

Expected: Planned changes are listed, without file copies. This does not establish that destination security metadata can be written.

6.3 Perform an actual small copy

PowerShell 
robocopy '\\FS01\DataMoverPilot' '\\FS02\DataMoverPilot' `
  /E /COPYALL /DCOPY:DAT /ZB /MT:8 /R:2 /W:3 /XJ /TEE
$LASTEXITCODE

Robocopy return codes 0–7 are generally non-fatal but may require review; 8 or higher indicates failure. Verify actual output and copied files.

6.4 Compare security descriptors

PowerShell 
(Get-Acl '\\FS01\DataMoverPilot\test.txt').Sddl
(Get-Acl '\\FS02\DataMoverPilot\test.txt').Sddl

Review expected ACL inheritance and identity differences. SACLs require separately authorized security-descriptor inspection. For 10–100 TB migrations, implement automated ACL and integrity validation rather than relying on sample checks alone.

7. Validate unattended execution

After the v1.3 worker service exists, run a scheduled pilot with no user logged on, then reboot the worker host and repeat. Verify the process identity and logs:

PowerShell 
Get-CimInstance Win32_Service |
  Where-Object { $_.Name -like '*DataMover*' } |
  Select-Object Name, State, StartName, StartMode

Check Windows Event Viewer, worker audit records, Robocopy exit codes, file results, and scheduled run timestamps. Absence of a UAC prompt alone is not proof of success.

8. Production cutover and rollback

Initial copy + scheduled incremental sync
↓
Dry-Run + file and ACL validation
↓
Freeze source writes and confirm quiescence
↓
Final Robocopy delta pass
↓
Revalidate + separate cutover approval
↓
Redirect approved SMB / DFS clients

Preserve original share paths, DFS targets, access controls, and source data for a defined rollback window. Document how to handle writes made to the destination after cutover; reversing Robocopy is not automatically a safe rollback.

Do not enable destructive mirroring (for example /MIR) by default. Destination-only files should not be removed without explicit change approval and validated recovery options.

Troubleshooting quick reference

Test-ADServiceAccount returns False

Verify KDS key readiness, AD replication, gMSA authorization group, host computer membership, DNS and Kerberos. Restart the host after membership changes if needed.

Dry-Run succeeds but actual copy fails

Dry-Run does not exercise all destination writes. Check share and NTFS access, backup/restore/security privileges, destination filesystem support, and Robocopy logs.

Scheduled jobs fail after logoff

Verify the worker is a real Windows service, its logon identity, gMSA readiness, service recovery, network access, and whether credentials or mapped drives were tied to an interactive session. Prefer UNC paths.

Permissions differ after copy

Inspect /COPYALL results, destination filesystem capabilities, inherited ACLs, identity resolution, SACL privileges, and security-descriptor comparison logic.

Robocopy reports a nonzero exit code

Robocopy exit codes are bit flags. Codes below 8 are generally non-fatal; review extra or mismatched files. Codes 8 and above signal failures.
